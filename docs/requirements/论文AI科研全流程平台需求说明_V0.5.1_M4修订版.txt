0.1 本次修订的反思与原则

本次修订重点纠正两类容易伤害产品可用性的“过度限制”：

第一，隐私保护不能以破坏研究分析为代价。
- “脱敏”不是把材料删到无法分析；
- 身份信息、研究变量、正文内容和伦理限制必须分层处理；
- 系统需要在再识别风险与分析保真度之间取得平衡；
- 任何处理副本都不得静默改变样本关系、说话人边界、实验条件、时间顺序或研究变量；
- 用户应能预览处理结果，并知道哪些字段被保留、替换或删除。

第二，功能可用性不应按学历或论文级别机械限制。
- 课程论文、课堂展示、文献汇报、小组汇报同样可以生成 PPT；
- PPT 能否生成应取决于材料是否足够、用户选择的场景和内容真实性，而不是“是不是硕博论文”；
- 没有真实结果时可以生成研究计划型或文献汇报型 PPT，但不得伪造结果页。

第三，阶段说明必须反映真实项目进度。
- M3 已完成，当前进入 M4；
- M4 应实现数据模型、Repository/API、权限、状态与版本持久化；
- 真实第三方模型调用、真实 BYOK、自动隐私处理和 PPTX 渲染仍按后续阶段实施；
- 不因修订需求退回 M3，也不允许跳过 M4 直接进入生产调用。

第四，平台避免“全发或全禁”的二元决策。
- 同一材料可以针对不同任务采用不同处理方式；
- 同一项目中的材料默认可被项目内部检索，但外部模型只获得当前任务所需的处理副本；
- 高风险材料可以转为本地处理、汇总分析或完全禁止外传。


==================================================
一、产品愿景与定位
==================================================

1.1 产品愿景

本平台不是普通聊天框，也不是“一键生成整篇论文”的代写工具。

平台核心形态为：

论文项目管理
＋材料解析与项目知识库
＋渐进式项目诊断
＋研究 Idea 与文献发现
＋章节写作与修改
＋多模型独立审阅
＋引用与证据核验
＋版本与责任追踪
＋投稿返修
＋科研图件
＋课程汇报、学术展示与答辩 PPT
＋DOCX、PPTX、图件和返修信等交付

1.2 核心价值

帮助用户把“模糊想法、零散材料、课程或导师要求、已有初稿、文献和数据”逐步转化为：

- 可执行的研究方案；
- 可追踪的论文项目；
- 有来源、有证据、有版本的论文内容；
- 可审阅、可修改、可回退的 AI 产出；
- 可交付的论文、返修信、图件和汇报材料。

1.3 核心差异化

平台不以“模型更强”作为主要差异化，而以科研工作流治理作为差异化：

- AI 先理解项目，再生成；
- 用户不知道答案时允许“不知道”；
- AI 推测不得冒充用户事实；
- 每个重要结论尽可能绑定证据；
- 生成模型与审阅模型职责分离；
- 多模型冲突显示依据，不以多数票代替事实；
- 原稿永不覆盖；
- 每次生成、修改、恢复和汇总都创建新版本；
- 用户最终决定采用哪个版本；
- 项目材料、模型调用和数据流向可审计。

二、目标用户与产品分层
==================================================

2.1 目标用户范围

平台支持以下用户：

A. 本科课程论文、本科毕业论文、课堂展示和小组汇报用户；
B. 本科高年级及硕士阶段，已有材料但研究设计不清晰的用户；
C. 硕博研究生、学位论文、期刊投稿和正式学术汇报用户。

2.2 核心用户

默认核心用户为：

“本科高年级＋硕士阶段，已有题目、要求、初稿、文献或部分数据，但不清楚如何形成完整研究设计和可信论文的用户。”

2.3 使用复杂度分层

同一平台通过场景、任务风险和材料成熟度调整复杂度，不建设三套独立产品，也不按学历机械封锁功能。

入门模式：
- 课程论文；
- 课堂展示；
- 小组汇报；
- 本科论文；
- 快速诊断；
- 简化 Skill；
- 课程论文 PPT、文献汇报 PPT；
- 渐进展示高级能力。

标准模式：
- 本科高年级；
- 硕士论文；
- 完整诊断；
- 章节、证据、版本和双模型审阅；
- 课程/组会/中期汇报 PPT；
- DOCX 导出。

进阶模式：
- 博士论文；
- 正式期刊投稿；
- 高级审稿；
- 数据声明；
- 返修；
- 严格证据验证；
- 复杂科研图件；
- 答辩、会议和投稿汇报 PPT。

课程论文用户可以使用 PPT、图件、文献矩阵和双模型审阅；系统只按任务就绪度、风险、费用和材料情况调整能力，不按学历禁止。

2.4 场景识别优先于学历识别

创建项目时优先询问任务场景，而不是只询问学历：

- 课程作业；
- 课堂展示；
- 小组汇报；
- 文献汇报；
- 本科毕业论文；
- 硕士/博士学位论文；
- 期刊或会议论文；
- 研究计划；
- 开题、中期或毕业答辩；
- 组会；
- 已收到审稿意见的返修项目。
三、产品基本原则
==================================================

3.1 先理解，再生成

系统应先理解：

- 用户目标；
- 论文类型；
- 已有材料；
- 课程、学校、导师或投稿要求；
- 当前任务；
- 当前缺口；
- 本次可用证据。

信息不足时，系统应提示缺口、推荐下一步或进入引导梳理，而不是直接补造事实。

3.2 诊断卡不是考试

用户使用平台往往正是因为不了解研究问题、理论、方法或统计设计。

所有专业字段必须允许：

- 暂不确定；
- 不知道；
- 暂时跳过；
- 稍后补充；
- 不适用；
- 请 AI 根据材料推测。

3.3 AI 推测不等于事实

AI 推测必须：

- 标明为 AI_INFERRED 或 PENDING_CONFIRMATION；
- 展示推测依据；
- 展示来源材料和位置；
- 展示置信度；
- 提供确认、修改或拒绝入口。

未经用户明确确认，不得保存为 USER_CONFIRMED。

3.4 原稿不可覆盖

- 上传初稿后创建不可覆盖的原始版本；
- AI 生成创建新版本；
- AI 修改创建新版本；
- 汇总 AI 创建候选版本；
- 用户人工编辑可保存新版本；
- 恢复旧版本也创建新版本；
- 不直接覆盖任何历史版本。

3.5 可检索不等于全部外传

项目内 AI 任务默认可以检索本项目资料，但外部 API 每次只接收完成当前任务所需的最小必要内容。

3.6 人类最终决策

以下事项必须由用户最终确认：

- 项目主要起点；
- AI 推测字段；
- 正式诊断卡；
- 正式研究问题和理论框架；
- 多模型冲突；
- 审阅意见是否采纳；
- 汇总候选稿是否成为采用版本；
- 正式引用和证据状态；
- 最终导出范围；
- 模型选择、费用和外部数据传输。

3.7 不虚构科研事实

禁止：

- 虚构数据；
- 虚构实验；
- 虚构样本；
- 虚构访谈；
- 虚构统计结果；
- 虚构 DOI、页码、仓储号或引用；
- 将搜索摘要当作全文证据；
- 用模型多数意见代替原始证据。

四、账号、数据保存与商业模式
==================================================

4.1 账号规则

已确认：

- 不允许游客试用；
- 手机号和邮箱作为账号标识；
- 一个手机号不能绑定多个账号；
- 手机号和邮箱在数据库中唯一；
- 用户可以修改绑定手机号和邮箱；
- 修改绑定信息属于敏感操作，正式上线前需验证码或等价验证；
- 不主动限制多人共享账号，因为模型和平台消耗与额度相关；
- 系统仍应记录登录设备、IP、失败原因和异常访问。

4.2 数据保存

已确认方向：

- 用户数据保存周期暂定为 1 个月。

待正式上线前明确：

- 1 个月从创建日起、最后活跃日起、会员到期日起还是删除日起计算；
- 哪些数据属于长期用户主动保留；
- 导出文件、日志、审计记录、备份和已删除项目各自保存多久；
- 用户是否可以付费延长；
- 到期前提醒方式；
- 删除与恢复窗口。

在上述起算点未确认前，代码中不得把“30 天后永久删除”写死为不可逆行为。

4.3 平台模型与 BYOK

平台同时支持：

A. 平台统一提供模型；
B. 高级或特殊用户绑定自己的 API Key（BYOK）。

平台模型：
- 模型费用由平台承担；
- 用户消耗包含模型费用和服务费用的平台积分；
- 平台负责路由、调用、失败处理和成本控制。

用户自带 Key：
- 模型费用由用户的供应商账户承担；
- 平台仍收取较少的编排服务积分；
- 服务积分覆盖材料检索、上下文编排、任务调度、审阅合并、版本保存、证据绑定、失败恢复和导出处理。

4.4 计费透明

每次任务开始前必须区分：

- 第三方模型预计费用；
- 平台服务积分；
- 使用平台凭证还是用户凭证；
- 每个模型的调用角色；
- 预计调用次数；
- 预计耗时；
- 预计发送的材料范围。

不得让用户误以为平台积分包含其自带 Key 的供应商费用。

4.5 失败计费原则

- 尚未发送模型：不扣模型相关积分；
- Key 无效：不扣；
- 平台编排失败且无产物：不扣或自动退回；
- 生成成功、审阅失败：仅结算已成功阶段；
- 用户取消：按实际已完成阶段结算；
- 供应商限流且无有效结果：不扣对应服务费；
- 已保存可用产物：按阶段结算；
- 自动重试不得造成无限扣费。

==================================================
五、项目创建与首次价值路径
==================================================

5.1 五种主要起点

首页保留五个清晰入口：

1. 从一个 Idea 开始；
2. 从已有初稿开始；
3. 从课程、学校、导师或投稿要求开始；
4. 从文献或参考论文开始；
5. 从数据或研究材料开始。

同时提供明显入口：

“我不知道怎么选，让 AI 帮我判断。”

5.2 主要起点不是项目类型

- 创建时单选一个 primary_creation_method；
- 它只决定首次导航和建议路径；
- 项目建立后可以继续添加所有其他材料；
- 同一项目可以同时包含 Idea、初稿、要求、文献、数据和其他研究材料；
- 不得因为主要起点不同建立互相隔离的五类项目模型。

5.3 AI 推荐起点

用户不知道时，系统询问三个最低问题：

1. 你大概想研究、写作或完成什么？
2. 你现在已经有什么材料？
3. 你希望 AI 首先帮助完成什么？

系统推荐一个主要起点并说明：

- 推荐结果；
- 判断依据；
- 已识别材料；
- 建议路径；
- 可替代起点。

用户必须确认或修改，不得静默自动进入。

5.4 上传优先，补问在后

已确认默认顺序：

选择入口
→ 上传或粘贴现有材料
→ 系统解析材料
→ 提取已知信息
→ 标记来源和置信度
→ 只补问材料中无法确认且会影响当前任务的问题
→ 生成诊断卡草稿

例外：
- 用户没有材料时，可以用文字描述直接进入 AI 引导梳理；
- 不得因未上传文件而阻止创建项目。

5.5 首次价值定义

首次价值不是“生成一段文字”，而是：

“系统识别用户当前所处阶段，并给出一条可信、可执行、可继续的下一步路径。”

首个有效结果可以是：

- 诊断摘要；
- 研究方向候选；
- 初稿问题地图；
- 要求约束清单；
- 文献主题聚类；
- 数据材料概览；
- 当前可开展任务和暂不可开展任务。

==================================================
六、项目材料、权限、分析保真与外部数据传输
==================================================

6.1 项目内材料默认访问

在同一项目内：

- 系统解析、索引、检索和任务编排模块默认可访问本项目所有资料；
- 项目 A 的任务不得读取项目 B；
- 用户不需要每次重新勾选几十份文件；
- 系统必须记录实际检索、处理和使用了哪些材料；
- “默认可检索”只适用于当前项目内部，不等于所有模型可获得原始材料。

6.2 外部模型最小必要发送

“项目内可检索全部资料”不等于“把全部资料发送给第三方模型”。

每次外部模型调用只发送：

- 当前任务所需正文；
- 必要诊断字段；
- 必要要求；
- 相关证据片段；
- 必要前后文摘要；
- 经确认保留的研究变量和结构信息。

默认不发送：

- 与当前任务无关的全文；
- 全部原始数据；
- 无关个人笔记；
- 密钥和账号信息；
- 其他项目内容；
- 当前任务不需要的身份信息；
- 未经许可或不满足伦理条件的材料。

6.3 材料风险维度

系统不得只给材料打一个模糊的“敏感/不敏感”标签，应至少区分：

- 直接标识符：姓名、手机号、邮箱、学号、身份证号、精确地址等；
- 间接标识符：过细年龄、极小地区、罕见职位、具体日期组合等；
- 敏感属性：健康、医疗、心理、财务、未成年人信息等；
- 研究必要变量：年级、专业、实验条件、分组、时间点、语言背景等；
- 普通研究正文：访谈内容、开放题答案、论文正文、公开材料等；
- 保密或伦理限制：企业机密、未公开核心数据、伦理审批限制外传内容；
- 版权限制：用户有权分析但无权向外部供应商传输的材料。

研究必要变量不得因为“脱敏”被无条件删除。

6.4 任务级处理方式

每个任务针对每份材料选择一种处理方式：

- RAW_ALLOWED：允许发送任务所需原文；
- SELECTIVE_REDACTION：选择性删除不必要字段；
- PSEUDONYMIZED：用 P01、P02 等伪匿名标识替换直接身份；
- AGGREGATED_ONLY：只发送统计汇总、编码表或结构化摘要；
- LOCAL_ONLY：仅允许本地模型或本地受控处理；
- EXTERNAL_BLOCKED：禁止发送任何外部模型。

同一材料在不同任务中可采用不同方式。

例如：
- 访谈主题分析可使用 PSEUDONYMIZED；
- 统计结果写作可使用 AGGREGATED_ONLY；
- 涉及伦理禁止外传的原始数据使用 LOCAL_ONLY 或 EXTERNAL_BLOCKED；
- 公开课程要求可使用 RAW_ALLOWED。

6.5 分析保真原则

隐私处理不能破坏研究有效性。

生成处理副本时必须尽量保留当前任务所需的：

- 说话人边界；
- 参与者稳定编号；
- 时间顺序；
- 轮次关系；
- 变量名；
- 实验条件；
- 分组关系；
- 缺失值状态；
- 数值精度；
- 引用位置；
- 文档结构；
- 编码单位。

禁止静默：

- 合并不同参与者；
- 改变样本数量；
- 删除关键实验条件；
- 打乱时间顺序；
- 把精确数据改成近似数据却不提示；
- 删除会改变研究结论的变量；
- 用 AI 自动补全被删除内容。

系统在发送前执行“分析保真检查”，并输出：

- 本任务必须保留的信息；
- 已删除或替换的信息；
- 可能影响分析的变化；
- 当前处理副本是否仍适合该任务；
- 需要用户确认的风险。

6.6 伪匿名映射

伪匿名流程：

原始材料
→ 项目内生成处理副本
→ 外部 AI 只分析处理副本
→ AI 返回 P01/P02 等结果
→ 平台在项目内部关联原材料和分析结果

要求：

- P01 等编号在同一项目和同一研究中保持稳定；
- 映射表只保存在项目内部；
- 映射表加密；
- 映射表不发送给外部模型；
- 普通日志不保存原始身份值；
- 导出默认使用伪匿名编号；
- 用户无权限时不得反向还原身份；
- AI 不得尝试推断或重建真实身份。

6.7 用户预览与确认

执行外部调用前显示：

- 供应商和模型；
- 处理方式；
- 将发送的处理副本；
- 保留的研究变量；
- 替换或删除的字段；
- 可能影响分析的地方；
- 不会发送的材料；
- 预计 Token 和费用；
- 用户排除、更换模型、改为本地处理或取消的入口。

对于普通公开材料，可允许用户保存低风险默认偏好。
对于高风险材料，每次外部传输必须明确确认。

6.8 材料权限设置

材料可设置为：

- 允许所有已批准模型使用；
- 仅允许指定供应商；
- 仅允许本地处理；
- 每次询问；
- 仅允许发送处理副本；
- 仅允许汇总；
- 禁止 AI 使用。

6.9 不适合外部模型的材料

以下材料不应仅凭“做过脱敏”就默认允许外传：

- 伦理审批明确禁止外传的数据；
- 无法充分降低再识别风险的小样本数据；
- 高度敏感医疗或心理数据；
- 未公开企业核心机密；
- 用户没有合法处理权限的第三方材料；
- 脱敏后会破坏研究结论的数据；
- 版权或合同禁止发送给第三方处理方的全文。

系统应推荐 LOCAL_ONLY、AGGREGATED_ONLY 或 EXTERNAL_BLOCKED，并解释原因。

6.10 每次调用审计

至少记录：

- project_id；
- task_id；
- provider；
- model；
- credential_source；
- 原始材料 ID；
- processing_mode；
- 处理副本 ID；
- 实际发送字段和片段；
- 被排除字段；
- 保真检查结果；
- 用户确认记录；
- 输入输出 Token；
- 费用估算和实际返回信息；
- 任务结果；
- 失败原因；
- 时间。

不得在普通日志、报错和前端状态中保存不必要的直接身份原文。
七、渐进式诊断卡
==================================================

7.1 功能目标

解决用户不了解专业问题、敷衍填写、随意编造或因长表单退出的问题。

诊断卡应帮助用户从“不知道”逐步走向“知道下一步”，而不是测试用户是否已具备完整研究设计。

7.2 创建时最低信息

初次创建只强制：

1. 大概想研究或完成什么；
2. 已有何种材料；
3. 希望 AI 首先帮助完成什么。

其余字段渐进补充。

7.3 诊断方式

提供：

- 快速开始；
- AI 引导梳理；
- 从材料自动提取；
- 完整专业填写。

AI 引导梳理内部提供：

快速梳理：
- 最多 3 个关键问题；
- 尽快得到下一步。

标准梳理：
- 默认模式；
- 通常 5—8 个问题；
- 达到当前任务最低可执行条件后停止。

深度梳理：
- 用户主动选择；
- 系统梳理研究对象、问题、理论、方法、数据、证据、交付和风险；
- 仍有问题上限，不允许无限追问。

7.4 字段状态

统一支持：

- USER_CONFIRMED
- AI_INFERRED
- PENDING_CONFIRMATION
- UNKNOWN
- SKIPPED
- MISSING_MATERIAL
- NOT_APPLICABLE

7.5 字段来源

状态与来源必须分开记录：

- USER_INPUT
- MATERIAL_EXTRACTED
- AI_RECOMMENDED
- SYSTEM_DERIVED
- IMPORTED

7.6 AI 推测显示

每个 AI 推测字段显示：

- 推测内容；
- 推测依据；
- 来源材料；
- 来源位置；
- 置信度；
- 当前状态；
- 确认；
- 修改后确认；
- 保留待确认；
- 拒绝；
- 标记不适用。

7.7 诊断卡建议字段

- 暂定题目；
- 论文类型；
- 场景；
- 目标语言；
- 目标字数；
- 截止日期；
- 研究背景；
- 研究对象；
- 核心问题；
- 研究目的；
- 研究意义；
- 研究问题或假设；
- 理论框架；
- 数据来源；
- 样本或语料；
- 研究方法；
- 分析方法；
- 已有材料；
- 缺失材料；
- 课程、学校、导师或投稿硬性要求；
- 引用格式；
- 伦理与隐私要求；
- 主要风险；
- 推荐结构；
- 当前可开展任务；
- 暂不适合开展任务；
- 建议下一步。

7.8 版本规则

- AI 首次生成时创建 DRAFT；
- 引导过程保留草稿历史；
- 待确认版本为 PENDING_CONFIRMATION；
- 用户确认后创建 CONFIRMED；
- 新确认版本使旧确认版本成为 SUPERSEDED；
- 可归档为 ARCHIVED；
- AI 不得直接修改已确认版本；
- 恢复旧版本仍创建新版本。

八、AI 引导梳理（参考 grill-me）
==================================================

8.1 产品定位

- 用户侧名称：“AI 引导梳理”；
- 属于“项目诊断与提纲”内部模式；
- 不新增第七个产品 Skill；
- 参考逐层追问思想，但不直接安装、暴露或无限运行第三方 Skill；
- M3 先用 Mock 问题树，M5 再接真实动态模型。

8.2 核心交互

每次只提出一个问题。

提出问题前优先读取：

- 已填写信息；
- 已授权材料；
- 现有诊断卡；
- 项目要求；
- 已有版本；
- 当前任务。

能从材料可靠提取的信息不得重复询问用户。

8.3 每个问题包含

- 问题；
- 为什么要问；
- 该答案影响什么；
- AI 推荐答案；
- 推荐理由；
- 候选选项；
- 自定义输入；
- 不知道；
- 暂时跳过；
- 稍后决定；
- 请 AI 根据材料推测；
- 不适用。

8.4 问题优先级

1. 当前任务阻塞项；
2. 影响多个后续决策的父级问题；
3. 材料无法确认的信息；
4. 高风险真实性问题；
5. 当前最有价值的澄清项。

先问父级，再问依赖它的子级。

8.5 不知道后的处理

用户选择“不知道”时，不重复逼问。

系统可：

- 推荐 2—3 个候选；
- 展示类似研究常见做法；
- 说明需要补充什么材料；
- 转入文献探索；
- 暂时跳过；
- 等上传材料后再判断。

8.6 停止条件

满足任一条件即停止：

- 当前任务信息已足够；
- 后续问题不影响下一步；
- 用户选择稍后补充；
- 连续两次选择不知道；
- 必须上传新材料；
- 达到模式问题上限；
- 用户主动结束；
- 用户切换模式；
- 继续只能得到低可信度推测；
- 问题属于后续阶段。

停止不代表失败。

8.7 结束摘要

展示：

- 当前已知；
- AI 推测但待确认；
- 尚待确认；
- 缺少材料；
- 现在可以开展的任务；
- 暂时不适合开展的任务；
- 建议下一步。

不得只显示“必填项未完成”。

8.8 问题数据契约

至少记录：

question_id
session_id
topic
field_key
parent_question_id
depends_on_answer
question
why_this_matters
decision_impact
recommended_answer
recommendation_reason
options
allow_custom_answer
allow_unknown
allow_skip
allow_ai_inference
blocking_level
source_material_ids
source_locations
answer
answer_status
answer_source_type
confidence
asked_at
answered_at

10.1 项目诊断与提纲

- 渐进式诊断；
- AI 引导梳理；
- 从材料提取；
- 诊断卡草稿和确认；
- 提纲生成；
- 缺口和下一步；
- 不直接生成完整论文。

10.2 文献总结与矩阵

- 理论；
- 方法；
- 数据；

- 结论；
- 局限；

读取：

- 当前已确认诊断卡；
- 当前章节；

- 项目要求；
- 用户允许的材料；
- 证据；
- 目标语言和字数。

信息不足时先返回缺口，不把推测写成研究事实。

10.4 通用修改

- 润色；

- 精简；

10.5 一致性检查

检查：

- 研究问题与方法；
- 方法与结果；
- 结果与讨论；
- 讨论与理论；
- 结论与研究问题；
- 样本、变量和术语一致性；
- 章节冲突；
- 过度声明；
- 缺少证据的重要判断。

10.6 引用与证据检查

- 正文引用与参考文献对应；
- Claim 与 Evidence Binding；
- 来源文件；
- 页码、段落和片段；
- DIRECT；
- INDIRECT；
- UNVERIFIED；
- 无法验证明确警告。

十一、科研全流程扩展模块
==================================================

11.1 Idea 创新性探索

- 从模糊想法生成多个候选方向；
- 标明研究对象、变量、方法、价值和可行性；

- 不承诺绝对新颖；

- 用户选择后加入项目；
- 支持 BibTeX/RIS；
- 不自动接入 Z-Library、安娜的档案、Sci-Hub 或其他未经授权来源；
- 不把搜索结果直接标为证据。

11.3 高级多视角审稿

可配置角色：

- 严格期刊审稿人；
- 方法审稿人；
- 统计审稿人；
- 理论审稿人；
- 语言与结构审稿人；
- 引用与证据审稿人。

输出：

- 总体判断；
- Major concerns；
- Minor concerns；
- 章节定位；
- 风险等级；
- 修改建议；
- 可转化的返修任务。

审稿报告不直接修改正文。

11.4 数据声明与投稿准备

- Data Availability Statement；
- 数据来源；
- 数据仓储；
- 访问条件；
- 第三方数据；

- 用户确认；

11.5 审稿意见与返修工作台

流程：

上传决定信和审稿意见
→ Reviewer 和 Comment 拆分编号

→ 修改创建新版本

- 修改前后对照；
- 未完成实验警告；
- Comment 状态；

11.6 科研图件中心

科研视觉：
- 机制图；
- 理论框架图；

安全要求：

11.7 科研汇报、课程展示与答辩 PPT

PPT 是所有适用项目的交付能力，不按学历、论文级别或是否投稿进行限制。

场景至少支持：

- COURSE_PRESENTATION：课程论文汇报；
- CLASSROOM_PRESENTATION：课堂展示；
- LITERATURE_REVIEW_PRESENTATION：文献汇报；
- GROUP_PRESENTATION：小组汇报；
- FINAL_COURSE_PRESENTATION：期末展示；
- RESEARCH_PROPOSAL：研究计划；
- PROPOSAL_DEFENSE：开题答辩；
- MIDTERM_DEFENSE：中期答辩；
- THESIS_DEFENSE：毕业答辩；
- LAB_MEETING：组会；
- CONFERENCE_PRESENTATION：会议汇报；
- PAPER_SHARING：论文分享；
- SUBMISSION_PRESENTATION：投稿或项目汇报。

PPT 可从以下来源生成：

- 已采用论文版本；
- 当前章节集合；
- 文献集合；
- 文献矩阵；
- 诊断卡和研究计划；
- 课程或导师要求；
- 审稿报告和返修状态；
- 用户选定的材料集合。

课程论文不需要先完成完整论文才能使用 PPT。
例如：
- 只有文献时，可生成文献汇报；
- 只有研究计划时，可生成研究计划展示；
- 已有课程论文时，可生成课程汇报；
- 已有分析结果时，可生成结果型汇报。

内容真实性规则：

- 没有真实结果时，不得生成伪造的结果、统计图或结论；
- 可使用“预期结果”“待验证假设”“计划分析”页面，但必须明确标注；
- 生成前检查来源内容是否足够；
- 引用、图件和结论必须绑定来源；
- 用户选择哪个论文或材料版本，PPT 就绑定哪个版本。

生成配置：

- 汇报场景；
- 听众；
- 目标时长；
- 预计页数；
- 语言；
- 学术正式度；
- 视觉风格；
- 是否需要讲者备注；
- 是否需要互动问题；
- 是否需要参考文献页；
- 是否需要问答准备。

生成结果：

- 叙事结构；
- 幻灯片大纲；
- 每页标题；
- 每页核心信息；
- 主图和来源；
- 资产清单；
- 讲者备注；
- 问答准备；
- PPTX。

版本规则：

- PPT 项目绑定具体来源版本或材料快照；
- 每次重新生成创建新 PPT 版本；
- 不覆盖旧 PPT；
- 来源内容更新后，旧 PPT 不自动改变；
- 系统提示是否基于新论文版本重新生成；
- 用户确认后才标记为采用版本。

PPT 就绪状态：

- READY；
- READY_WITH_WARNINGS；
- NEEDS_CONTENT；
- NEEDS_CONFIRMATION；
- BLOCKED。

阻断应基于内容真实性、材料权限和任务就绪度，而不是用户学历或论文类型。

==================================================
十二、多模型生成、独立审阅与汇总
==================================================

12.1 核心原则

多模型不是“多个 AI 重复回答”，而是不同模型承担不同职责。

统一角色：

- ROUTER：识别任务和建议流程；
- GENERATOR：生成初稿；
- REVIEWER：独立审阅；
- VERIFIER：核验证据和高风险事实；
- REVISER：根据用户选中的意见修改；
- AGGREGATOR：整合多个结果形成候选稿。

12.2 执行模式

快速模式：
- 仅 GENERATOR；
- 适合低风险草稿、简单润色或翻译。

标准模式：
- GENERATOR；
- REVIEWER；
- 用户查看问题；
- 可选调用 REVISER/AGGREGATOR 形成候选稿。

严格模式：
- GENERATOR；
- REVIEWER；
- VERIFIER；
- 用户选择意见；
- REVISER/AGGREGATOR 创建候选稿；
- 可选最终验证。

禁止无限自动循环。

默认最多进行：
- 一次自动修订；
- 一次最终验证。

任何额外调用必须重新显示成本并获得用户确认。

12.3 用户必须选择模型

已确认：

- 所有用户在每次正式 AI 任务前自行确认模型；
- 系统可以显示推荐标签、理由、费用和隐私等级；
- 系统不得替用户静默决定；
- 不得因失败静默切换到更贵模型；
- 切换供应商前重新确认数据范围和费用。

每个任务至少选择：

- 生成模型；
- 审阅模型（启用复核时）；
- 验证模型（严格模式时）；
- 汇总/修订模型（需要候选稿时）。

用户可以保存常用组合，但执行前仍须确认。

12.4 结果展示与最终版本

已确认采用：

“并排展示＋汇总 AI 生成候选稿＋用户最终确认”。

流程：

生成 AI → V1
审阅 AI → R1（报告，不修改 V1）
验证 AI → F1（可选）
用户选择要采纳的问题
汇总/修订 AI → V2 候选稿
用户对比 V1 与 V2
用户手动修改或确认
形成正式采用版本 V3

12.5 审阅结论

统一：

- PASSED
- PASSED_WITH_WARNINGS
- REVISION_REQUIRED
- BLOCKED
- REVIEW_FAILED

12.6 审阅问题

至少记录：

- severity；
- issue_type；
- location；
- original_text；
- reason；
- evidence_binding_id；
- suggested_action；
- source_model_run_id；
- user_decision；
- user_reason；
- resolution_version_id；
- status。

12.7 用户处理决定

- ACCEPT；
- PARTIALLY_ACCEPT；
- IGNORE；
- FALSE_POSITIVE；
- NEEDS_MORE_EVIDENCE；
- DEFER；
- USER_EDITED。

12.8 多模型冲突

区分：

事实冲突：
- 引用；
- 数据；
-统计；
- 样本；
- 方法；
- 研究结果。

逻辑冲突：
- 论证；
- 因果；
- 结果与结论边界。

规范冲突：
- 导师；
- 课程；
- 期刊；
- 格式。

表达偏好：
- 语气；
- 措辞；
- 段落风格。

处理规则：

- 不以多数票自动裁决事实；
- 不按模型评分高低代替原始证据；
- 合并重复问题但保留来源；
- 显示不同模型的依据；
- 低风险表达偏好可由用户授权系统处理；
- 高风险事实、证据和规范冲突必须用户决定；
- 证据不足时标记无法确认。

12.9 汇总 AI 约束

汇总 AI：

- 只处理用户选中的意见；
- 不得自动加入新事实、数据或引用；
- 每项修改关联审阅问题；
- 产生候选版本，不自动成为最终版本；
- 不覆盖 V1；
- 记录模型、材料、Prompt 版本和费用。

==================================================
十三、模型供应商、BYOK 与 API Key 安全
==================================================

13.1 Provider 架构

支持：

- OpenAI；
- Anthropic；
- DeepSeek；
- 其他经审核的兼容 API；
- 本地模型；
- Mock Provider。

具体模型版本由后台配置，不写死在业务代码中。

13.2 凭证来源

统一：

- PLATFORM_CREDENTIAL；
- USER_CREDENTIAL。

13.3 BYOK 功能

高级或特殊用户可以：

- 添加供应商；
- 输入 API Key；
- 测试连接；
- 查看掩码；
- 配置可用模型；
- 设置可用项目；
- 设置可承担角色；
- 禁用；
- 删除；
- 更换。

13.4 API Key 安全

- 不在浏览器持久保存明文；
- 不在前端日志保存；
- 不在错误信息返回；
- 服务端加密保存；
- 页面只显示掩码；
- 解密只发生在实际调用瞬间；
- 不能跨用户、跨组织访问；
- 删除后停止相关新任务；
- 不自动借用其他用户 Key；
- 不把 Key 发送给模型；
- 备份、日志和错误追踪中不得出现完整 Key；
- 密钥轮换和撤销需要审计。

M4 实现凭证元数据、权限、掩码、加密存储接口和审计契约，但不接收生产 API Key，也不执行真实供应商调用。
真实凭证接入、连接测试和模型调用在 M5 实现。

13.5 模型数量

第一版建议：

- 快速模式：1 个生成模型；
- 标准模式：2 个职责模型，修订阶段可复用或另选模型；
- 严格模式：最多 3 个主要职责模型；
- 自定义模式：最多配置 4 个模型角色；
- 超过限制需管理员或企业配置。

模型数量增加不代表质量必然提高。

==================================================
十四、费用估算与预算控制
==================================================

14.1 执行前估算

显示：

- 预计输入 Token；
- 预计输出 Token；
- 各模型费用区间；
- 平台服务积分；
- 总调用次数；
- 预计耗时；
- 费用由平台还是用户供应商承担。

14.2 单次最高预算

已确认：

- 用户可以设置本次任务最高 API 预算；
- 预计或执行中即将超过上限时暂停；
- 不自动继续；
- 提供缩短材料、减少模型、降低输出长度或更换模型建议；
- 用户再次确认后才能继续。

14.3 预算误差

- 明确费用是估算；
- 实际结算以供应商返回为准；
- 平台保存估算与实际差异；
- 不得以低估价格诱导用户；
- 对无法预测的调用显示高波动提醒。

14.4 后续可选

后续可以增加：

- 日预算；
- 月预算；
- 按供应商预算；
- 按项目预算；
- 组织预算；
- 额度告警。

单次预算为 V0.5 当前必要能力，周期预算可后续扩展。

十五、AI 任务状态、失败恢复与幂等

15.1 状态机

15.2 失败分类

- Key 无效；
- 额度不足；
- 供应商限流；
- 网络断开；
- 模型超时；
- 内容安全拒绝；
- 参数错误；
- 文件解析失败；
- 检索无结果；
- 证据不足；
- 用户取消；
- 平台内部错误；
- 预算不足。

15.3 有限重试

- 网络抖动：有限指数退避；
- 限流：等待后有限重试；
- 参数错误：不盲目重试；
- 内容安全拒绝：不得换模型规避；
- 检索无结果：最多调整检索词后有限重试；
- 长驻进程必须设置超时；
- 禁止无限循环。

15.4 部分成功

例如：

生成成功
→ 审阅失败

系统应：

- 保存生成版本；
- 标记“未完成独立审阅”；
- 不标记为已复核；
- 提供重试、换模型、稍后审阅或保留未审阅版本；
- 不丢弃已成功产物。

15.5 恢复审计

长任务断流或客户端中断后：

- 检查已落盘文件；
- 检查任务步骤；
- 检查模型 Run；
- 检查版本；
- 检查日志和测试；
- 区分已完成、未完成、状态不明；
- 对状态不明先验证产物；
- 只重跑最小未完成步骤；
- 不从头重复不可逆任务。

15.6 幂等

- 每个任务有唯一 idempotency_key；
- 重试不得重复扣费、重复写版本或重复导出；
- 数据库迁移、外部导出、模型回调和文件处理必须设计幂等；
- 恢复时不得静默创建重复版本。

十八、引用、文献与证据体系

18.1 文献状态分级

- SEARCH_CANDIDATE：搜索候选；
- METADATA_VERIFIED：元数据已核验；
- FULLTEXT_AVAILABLE：全文可用；
- CLAIM_EVIDENCE_VERIFIED：论断证据已核验。

不同状态不得混用。

18.2 Evidence Binding

记录：

- claim_id；
- literature_id；
- material_id；
- page；
- paragraph；
- source_location；
- original_excerpt；
- support_level；
- verifier；
- verification_status；
- verified_at。

支持等级：

- DIRECT；
- INDIRECT；
- UNVERIFIED；
- CONTRADICTED。

18.3 可信规则

- 摘要支持不等于全文支持；
- 搜索结果不等于证据；
- 元数据核验不等于论断核验；
- 多模型同意不等于证据确认；
- 未能定位原文必须警告；
- 文献不存在或元数据冲突时阻断正式引用；
- 参考论文只分析结构和规范，不复制内容。

二十七、Codex 开发执行方式
==================================================

27.1 小批次开发

不再让单次任务连续执行数小时到十几个小时。

每轮：

- 只完成一个明确批次；
- 建议工作量 30—90 分钟；
- 不跨多个里程碑；
- 开始前说明 Task ID、范围和停止条件；
- 完成后测试、提交、更新状态并汇报。

27.2 Agent 数量

- 同时写代码的子 Agent 默认最多 3 个；
- 任务完全独立时允许第 4 个；
- 不为展示并行而拆分；
- 根 Agent 负责集成；
- 每个 Agent 有互斥目录所有权；
- 共享契约由根 Agent 或 Contract Agent 修改。

27.3 Worktree

写代码 Agent 使用独立 worktree。

不得：

- 多 Agent 同时修改同一目录；
- 子 Agent 直接修改主 Schema、全局枚举、路由、导航或环境模板；
- 未审查直接合并。

27.4 测试策略

开发过程中：
- 受影响文件 lint；
- 局部测试；
- 页面局部检查。

里程碑审核门：
- 全仓 lint；
- typecheck；
- build；
- E2E；
- 浏览器；
- 控制台；
- 服务端日志；
- 截图；
- 导出打开；
- 验收矩阵。

27.5 长驻进程

dev server/watch：

- 后台启动；
- 保存 PID；
- stdout/stderr 写真实日志；
- 启动超时 60 秒；
- 健康检查；
- 测试后关闭准确 PID；
- 不等待不会退出的命令；
- 不 taskkill 所有 node.exe。

27.6 Git

每个小批次：

- 检查 git status；
- 审查未跟踪文件；
- 不盲目 git add -A；
- 排除日志、PID、密钥、缓存和不应提交的构建产物；
- git diff --check；
- 局部测试；
- 创建清晰 commit；
- 不累计大量未提交改动。

27.7 阶段门

- 前端增量先真实渲染；
- 用户审核前不执行不可逆迁移；
- Mock 明确标识；
- Skill 审计不等于已接入；
- 用户未批准不跨阶段；
- 用户未要求不部署。

三十三、最终产品定义
==================================================

V0.5.1 的最终定义：

“一个面向本科课程论文、本科高年级、硕士生及进阶科研用户的论文 AI 科研全流程平台。平台允许用户从 Idea、初稿、要求、文献或数据开始，通过渐进式诊断和一次一问的 AI 引导梳理明确项目；在项目内统一管理材料、章节、证据和版本；根据任务对材料进行原文、选择性删除、伪匿名、汇总、本地处理或禁止外传，在保护隐私的同时保留研究分析所需变量和结构；由用户选择生成、审阅、验证和汇总模型，在明确费用、预算和数据传输范围的前提下完成多模型协作；所有 AI 推测、引用、修改和最终采用版本均可追踪；平台支持课程论文汇报、课堂展示、文献汇报、小组汇报、组会、答辩和会议 PPT，并以材料就绪度和内容真实性而非学历决定功能可用性；平台始终由用户掌握事实确认、模型选择、费用、数据外传和最终版本决定权。”
