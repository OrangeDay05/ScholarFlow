# M3 增量 Mock 审核报告

更新时间：2026-07-27

## 1. 审核范围

本审核包覆盖两个不改写 M2 的前端增量：

1. “项目诊断与提纲”内部的渐进式诊断与“AI 引导梳理”；
2. 多模型编排与用户自带 API Key 的前端 Mock 和数据契约。

M2 的登录、项目列表、五种创建入口、诊断卡、论文目录、三栏编辑器、章节版本、引用证据和 DOCX 预检继续作为视觉与交互基线。

## 2. 页面路由

| 路由 | 审核内容 |
|---|---|
| `/projects/new/idea` | 三个最低创建问题、快速进入项目 |
| `/projects/demo/diagnosis` | 四种诊断入口、单问题引导、结束摘要与版本展示 |
| `/projects/demo/editor?section=introduction` | 任务级就绪状态、严格复核的验证模型与模型配置入口 |

| `/admin/models-skills` | 管理端多模型编排 Mock 摘要与入口 |

## 3. 渐进式诊断 Mock

- 初次创建只要求“想完成什么、已有材料、希望 AI 先做什么”三个基础问题。
- 诊断首页提供快速开始、AI 引导梳理、从材料自动提取、完整专业填写四种入口。
- 标准与深度梳理每次只显示一个问题，并展示提问原因、决策影响、推荐答案、依据和材料来源。
- 用户可选择不知道、跳过、不适用、AI 推测或稍后决定。
- 字段状态与来源分开记录；AI 推测不会显示为用户确认事实。
- 连续两次“不知道”、达到问题上限、当前任务已就绪或缺少新材料时停止追问。
- 结束摘要区分当前已知、AI 推测、尚待确认、缺少材料、可开展任务与暂不适合任务。
- 草稿、确认和恢复均以追加版本展示，不覆盖历史版本。

## 4. 多模型编排与用户 API Key Mock

- 角色统一为 `GENERATOR`、`REVIEWER`、`VERIFIER`、`REVISER`、`ROUTER`，各角色独立记录。
- 标准模式使用两个模型；严格模式最多三个模型；自定义模式最多四个模型。
- 每种模式都规定最大调用次数、超时和停止条件，禁止模型间无限循环。
- 任务可以分别指定生成、审阅与验证模型，并显示供应商、模型、角色和凭据来源。
- 凭据类型区分 `PLATFORM_CREDENTIAL` 与 `USER_CREDENTIAL`。
- 用户 Key 页面可演示供应商、掩码、模型范围、项目范围、允许角色、测试连接、禁用和删除。
- 真实 Key 输入框在 M3 中保持禁用；页面不调用供应商、不把 Key 写入浏览器存储或日志。
- 执行前展示模型、平台额度或用户 Key、预计调用次数、材料、数据处理方、耗时和降级方案。
- 多模型意见可合并重复问题，但保留每个模型来源；冲突意见及各自依据并列显示。
- 多模型一致不等于事实确认；事实和引用仍要求回到授权原始材料核验。
- 审阅模型只生成报告，验证模型只生成验证报告，最终采纳由用户决定。
- 覆盖生成失败、审阅失败、验证失败、部分超时、Key 无效、额度不足、限流和用户取消八种失败状态。
- 部分失败保留已成功产物，未完成流程不会标记为通过。

## 5. 数据契约

本轮前端契约位于：

- `app/lib/progressive-diagnosis-mock.ts`
- `app/lib/model-orchestration-mock.ts`

契约覆盖问题树、字段状态/来源、任务就绪、诊断版本/审计、模型角色、父子阶段、凭据类型、模型意见、冲突、调用预算、停止条件和失败产物保留。

这些类型尚未写入正式数据库，也没有迁移。

## 6. 功能开关

## 8. Mock 与真实能力边界

当前没有：

- 收集或保存真实 API Key；
- 服务端加密；
- 真实供应商连接测试；
- 真实模型路由、生成、审阅或验证；
- 正式模型编排数据库字段或迁移；
- 新增真实 Skill；
- 生产密钥；
- 生产部署。

页面中的模型、凭据、连接状态、意见、冲突、调用次数、耗时和失败结果均为 Mock。

## 9. 已知限制

- 页面交互状态保存在当前 React 会话，刷新后恢复 Mock 初始值。
- 用户 Key 输入被有意禁用，不能用于测试任何真实密钥。
- 数据契约尚未持久化，跨用户/组织隔离与服务端加密只能在后续真实实现中验证。
- 本轮使用 SSR、HTTP、源码测试和构建验证，没有增加视觉截图。
